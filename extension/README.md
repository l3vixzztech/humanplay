# humanplay — Chrome extension (MV3)

Milestone 6: **voice announcements**. The content script reads the live
chess.com game state (M3 DOM adapter), the side panel sends it to the local
Maia-3 server (`POST /analyze`, M4), renders the **top-3 human moves** with
probabilities and Maia's **human outcome prediction** (WDL), conditioned on an
editable **Elo pair**, **draws the top-1 suggestion as an arrow on the real
chess.com board** (thinner alternatives optional, M5) and now **speaks the
suggested move — "just the move"** ("Knight to f3") via `chrome.tts` from the
**service worker** (M6), with a "Voice (TTS)" card, a Ctrl+Shift+Y hotkey and a
toolbar badge. Still deliberately absent: opponent/premove prediction (M7),
commentary (M8). Pixel recognition is parked
(`../parked/image-recognition/`); the capture-source abstraction and the PNG
recorder remain as **debug tools**.

## Load it (dev)

1. Start the helper server (needed for suggestions; the panel works without it
   and says why):
   ```bash
   cd server && .venv/bin/python -m uvicorn app:app --host 127.0.0.1 --port 8765
   ```
2. `chrome://extensions` → Developer mode ON → **Load unpacked** → this
   `extension/` directory → pin **humanplay**.
3. Open a chess.com game (a bot game is fine), **click the humanplay toolbar
   icon** → the side panel opens; the state card fills in within ~1 s and the
   suggestion appears on your turn (target ≤ 1.5 s after the position changes;
   measured ~0.16 s with the real engine, see below).
4. Make a move — the state card, the suggestion and the **arrow on the board**
   update on every change (adapter debounce 150 ms; the previous position's
   arrows disappear the moment the board changes). On the opponent's turn the
   card shows "their turn — waiting" and the arrows clear (opponent prediction
   is M7). Toggle **Show arrows on board** / **Show alternatives** in the
   suggestion card.
5. Tick **Speak suggestion** in the **Voice (TTS)** card (default off) or press
   **Ctrl+Shift+Y** — on your turn the suggested move is spoken ("Knight to
   f3"); the toolbar badge shows a green **TTS** while it is on. Speech runs in
   the service worker: closing the panel does not stop it. On Linux Chrome
   needs a speech backend and `--enable-speech-dispatcher` (see "Voice (TTS)
   (M6)" below); the voices line in the card tells you what it found.

The content scripts are **classic scripts** (MV3 limitation), so they have no
static imports: `board-dom.js`, `move-history.js`, `board-locate.js`,
`overlay-geometry.js` and `vendor/chess.js` are loaded with
`import(chrome.runtime.getURL(...))` and listed in `web_accessible_resources`
(chess.com origins only). Both content-script files share one isolated world, so
the adapter publishes its freshest state on `globalThis.__humanplayAdapterState`
and calls `globalThis.__humanplayContentHook(state)` — that is how the overlay
re-anchors on every new GameState without a second DOM observer. The panel is a
normal ES-module page and imports `../analysis/analyze-client.js` directly. The
same module files run unchanged in Node for the zero-dep unit tests.

## The chess.com adapter (M3)

What it reads, all verified against live chess.com on 2026-10-16 (probe
evidence: `../test/fixtures/chesscom/README.md` and `.../reference/`):

| Datum | Primary | Fallbacks |
|---|---|---|
| board element | largest displayed `wc-chess-board` / `#board-single` / `#board-play-computer` / `#board-analysis-board` / `.board` (shared `board-locate.js` since M5) | — |
| position | `.piece` elements with `square-XY` classes (X = file digit a=1…, Y = rank digit 1…; absolute under flipping) | per-square containers with piece children; the FEN the board exposes (`board.game.getFEN()`, validated) |
| history | move-list nodes (`.node` in `wc-simple-move-list` / `wc-vertical-move-list` / `.move-list`…), timestamps `[data-move-list-el="timestamp"]` excluded, ordered by `data-node` ply | `board.game.getHistorySANs()` when no DOM list exists |
| flipped | `wc-chess-board.flipped` class | `board.state.isFlipped` |
| user color | bottom player's `clock-white`/`clock-black` token | `board.game.getPlayingAs()`; panel setting `settings.userColor`; flipped inference |

Every position strategy is verified by a **placement plausibility check**
(exactly one king per side, no pawns on rank 1/8, no duplicate squares, ≤ 32
pieces) — a strategy that parses but yields an impossible position is rejected
and the next one is tried. The log of which strategy won is in `strategyLog`
and is mirrored to `console.debug` (`[humanplay] position=… history=…`).

**Reconciliation (locked, `../docs/PROJECT.md`):** the board is the source of
truth for the position, chess.com's move list for the history. The SAN list is
replayed from the initial position with chess.js; if the replayed board field
differs from the DOM board field (or a move is illegal), the state carries a
`mismatch` object, the history is dropped for that update and `warnings`
explain any degraded metadata (`side to move unknown`, …). The panel renders
mismatch/warnings prominently **and** the analysis falls back to the board
position without history.

**GameState** (full field list and semantics: `../docs/PROJECT.md`):

```js
{ ok, fen, movesUci, userColor, flipped, boardRect{x,y,w,h}, devicePixelRatio,
  gameUrl, gameId, ts, mismatch?, boardId, turn, positionSource, historySource,
  historyStatus, warnings[], strategyLog[], sessionSeq, resetDetected, … }
```

`boardRect` is the 8×8 play area in **viewport CSS pixels** (`getBoundingClientRect`
of the board element) plus `devicePixelRatio` — everything M5 needs to draw an
arrow on the real board.

Messages: the content script broadcasts `humanplay:chesscom-state` on every
change; the panel can send `humanplay:get-state` (Refresh button, on open) and
`humanplay:record-snapshot` (see below).

## The analysis loop (M4)

`src/analysis/analyze-client.js` is the only place that talks to the server.
Contract details, error classes and the request builder are documented in the
file header; the short version:

- **Request building** (`buildAnalyzeRequest`): the adapter's `fen` is the
  *current* position and `movesUci` the *full* history, but `POST /analyze`
  wants a BASE position plus moves on top of it. So a replayed history is sent
  as **standard start position + the full UCI history** (Maia's history planes
  then see the real game, `--use-uci-history` semantics). With an adapter
  `mismatch` (or no usable history) the request is **board FEN + no moves** and
  the card shows the mismatch warning.
- **Fetch semantics**: `AbortController` timeout (4 s), **exactly one retry on
  a network failure** (connection refused/dropped — never on 4xx/5xx and never
  on a timeout). Results are never thrown at the caller:
  `{ok, status, data, roundTripMs, error, errorClass, attempts, …}` with the
  error classes `offline`, `timeout`, `invalid_input` (400/422),
  `engine_unavailable` (503), `http`, `bad_response`.
- **Position key + cache**: the key is `fen|moves|elo_self|elo_oppo|top_k`, so
  identical state re-emits (the adapter broadcasts often) never re-request; a
  small LRU (24) also answers when you come back to a position; failures are
  never cached. In-flight requests for the same key are shared (dedupe), so a
  slow request is not duplicated by a re-emit. `noteSessionSeq` clears the
  cache on a new game (`sessionSeq` change).
- **Stale guard**: the client remembers the *current* key (also via
  `expectKey()` when no request is made, e.g. on the opponent's turn). A
  response whose key is no longer current is returned with `stale: true` and the
  panel **discards it silently** — a new position always wins over an older,
  slower response.
- **Gating policy** (`analysisGate`): auto-analyze only when the assistant
  toggle is on **and** the adapter state is ok **and** the user's color is known
  **and** it is the user's turn. Otherwise: `waiting` ("their turn"),
  `no-color`, `off`, `no-state`. **Analyze now** works whenever a state is
  known (it forces a fresh request).
- **Elo**: `elo_self`/`elo_oppo` inputs (0–5000, clamped, default 2400,
  persisted in `settings`) are part of the position key, so changing them
  re-analyzes the current position. On the Ruy Lopez fixture the top move really
  changes with Elo (1200 → `d4` 83.6 %, 2600 → `h3` 86.2 %; evidence:
  `../test/fixtures/captures/analyze/real-elo-changes-top-move.json`).
- **WDL perspective**: the server's `wdl` is from the **side-to-move**
  perspective. Auto analysis runs on your turn, so the card labels it
  `human outcome prediction (you)`; a manual analysis on the opponent's turn
  flips win↔loss and labels it `opponent's perspective`. The "?" tooltip says
  explicitly that this is Maia's human-model value head and **not** an engine
  evaluation.
- **Game over**: the server answers `moves: []` plus a rules-decided WDL; the
  card shows "game over — checkmate — … is mated" (rows hidden) instead of
  suggestions.

## The board overlay (M5)

One canvas, drawn on the real board — `src/content/board-overlay.js` +
`src/content/overlay-geometry.js` + the shared `src/content/board-locate.js`.

**Message routing.** The panel owns the overlay policy and sends
`humanplay:suggestion` `{moves, topN, key}` / `humanplay:clear-suggestion`
`{reason, key}` with `chrome.runtime.sendMessage`. Content scripts cannot receive
runtime messages, so the **service worker forwards to the tab that most recently
reported a `humanplay:chesscom-state`** (tracked in memory + mirrored to
`chrome.storage.session` so MV3 worker restarts do not lose it). Multi-tab rule
(documented, intentional): the *last* game tab that emitted a state wins; a
sibling tab keeps the arrows it already had until its own next episode.

**Never stale.** The panel only publishes the suggestion of a result whose M4
position key is still current (the M4 stale guard runs first) and clears the
overlay on every state where the card does not show a current suggestion: a new
position starts analyzing, their turn, assistant off, `no-color`, game over,
`/analyze` error, stale result, or the "Show arrows" toggle off. The overlay adds
its own guard: it remembers the GameState signature (fen · UCI history · board ·
flipped · session) at accept time and clears when a different position arrives —
arrows cannot survive a move even if the panel goes away mid-game.

**Geometry** (pure, unit-tested, viewport CSS pixels):
`squareSize = min(w,h)/8`; `col = file`, `row = 7 - rank`, both inverted when
flipped; endpoints are the square centres (shown arrow: shaft from the source
centre to the head base + a 3-point arrowhead polygon pointing at the target).
Thickness = `16 %` of a square clamped to `[2, 42]` px and ≤ half a square
(alternatives `9.5 %`); tiny boards (`< 4 px` squares) and thumbnails
(`< 24 px` squares, e.g. chess.com preview boards) are not drawn at all.

**Canvas hygiene.** Exactly one canvas is added to `document.body`:
`position: fixed; inset: 0`, `pointer-events: none`, `aria-hidden`,
`display: none` while idle, and `z-index = max(40, board stack z + 1)` — above
the board, below chess.com's modals. Bitmap = `clientWidth/Height ×
devicePixelRatio`, drawing under `ctx.setTransform(dpr, …)` (DPR-crisp; CSS-px
geometry). Colours: solid orange top-1 with a dark outline, thin translucent
blue alternatives, plus a subtle from/to square highlight for the top-1 — all
readable on light and dark boards. Nothing else on the page is modified.

**Re-anchoring.** Geometry is recomputed from the live
`getBoundingClientRect()` on: every suggestion/clear, every new GameState,
`resize`, `scroll` (passive), a `ResizeObserver` on the board, and a bounded
re-attach retry when the board element disappears (SPA navigation → canvas
hidden, re-anchored when the board returns). No rAF loop when idle.

**Settings** (persisted in `settings`): **Show arrows on board** (default ON) and
**Show alternatives** (default OFF) — toggling takes effect immediately (clear /
re-render with the currently displayed, still-current suggestion).

## Voice (TTS) (M6)

The suggested move is spoken — **"just the move"**, no probabilities. Sources:
`src/tts/move-speech.js` (wording), `src/tts/tts-policy.js` (when),
`src/tts/speaker.js` + `src/tts/tts-service.js` (execution, in the **service
worker**), `src/ui/sidepanel.{html,js}` (the "Voice (TTS)" card).

**Wording** (`move-speech.js`, pure, zero-dep, Node-tested): `Nf3` → "Knight to
f3", `exd5` → "e-pawn takes d5", `O-O` → "Castle kingside", `e8=Q+` → "Promote
to queen on e8, check", `gxh8=N#` → "g-pawn takes h8, promote to knight, mate",
`Nbd2` → "b-knight to d2", `R1e2` → "rook one to e2", `Bxh7+` → "Bishop takes
h7, check". `+`/`#` → ", check"/", mate"; annotations and an `e.p.` marker are
stripped (en passant reads like a normal pawn capture). Unparseable SAN falls
back to the UCI phrasing ("move e2 to e4", "+ , promote to queen"); when
nothing parses the panel stays silent — it never speaks garbage.

**Policy** (`tts-policy.js`, pure): speak iff **TTS enabled** (default OFF) +
**assistant on** + state ok + color known + **your turn** + a suggestion is
ready for the **current** position key (the M4 stale guard runs first) + that
key has **not been spoken** before (bounded dedupe store; re-emitted states and
re-renders never repeat, a new game clears it). **Never**: opponent's turn
(auto *and* manual "Analyze now"), assistant off, any `/analyze` error, game
over, stale results. Switching TTS **on** (checkbox or hotkey) speaks the
current suggestion once (`force` bypasses only the dedupe); switching **off**
sends an immediate `stop()` — mid-sentence included.

**Where the speaker lives — and why.** The panel sends
`humanplay:tts-speak`/`:tts-stop`/`:tts-voices`; the **service worker** calls
`chrome.tts`. Verified on Chrome for Testing 155 (evidence in
`../test/fixtures/captures/tts/`): `chrome.tts` **is available in an MV3 service
worker** (speak/stop/getVoices/isSpeaking/onEvent, events fire, audio plays), so
no offscreen document is needed and the manifest grows exactly one permission.
The offscreen fallback from the plan was **dropped**: an offscreen document does
not even expose `chrome.tts` (only `speechSynthesis`), and `offscreen` was not in
the permission budget. Because the worker owns the speaker, **closing the side
panel does not stop speech** — the proof closes the panel, changes the position
and still records a speak through the production message path.

**Interruption.** Every `speak()` in the worker is preceded by `stop()` and
uses `enqueue:false`, so a new position always interrupts the previous sentence;
the record shows the stop→speak pair with timestamps.

**Linux/Chrome backend.** Chrome synthesizes only when it has a speech backend:
with `--enable-speech-dispatcher` (speech-dispatcher + espeak-ng installed)
`chrome.tts.getVoices()` enumerates **14805 voices** and utterances fire
start/end events; without the flag there are **0 voices** and every utterance
ends in `{type:"error"}` — the speak path still executes and is recorded. The
voice list is enumerated **asynchronously** (0 for the first moment after a cold
start), so the panel retries once after 2 s and the worker refreshes on
`chrome.tts.onVoicesChanged`. The card shows `voices: N · chrome.tts` and, when
the count is 0, an actionable note (install speech-dispatcher / start Chrome
with the flag). Quality note: espeak-ng is **robotic** — a Piper speaker can
slot into `createSpeaker()` later without touching callers.

**Controls.** **Speak suggestion** (default OFF, persisted), **rate** select
(0.8/1.0/1.2; clamped 0.5–2), **Speak test** (speaks "Knight to f3" regardless
of the toggle — it tests the voice, not the policy), and the voices line/note.
**Ctrl+Shift+Y** (`commands.toggle-tts`) toggles TTS from the worker (panel
closed included) and flips the **toolbar badge**: the text **"TTS"** on a green
(`#2f6f4f`) background with white text while on, cleared while off — 3
characters is the legible maximum for a Chrome badge. The panel checkbox
follows hotkey toggles through `chrome.storage.onChanged`.

**Recording.** `globalThis.__humanplayTts` (worker) logs every speak/stop call
(text, options `{enqueue:false, rate}`, engine, SAN/UCI, reason, source, key,
timestamps), the `chrome.tts` lifecycle events, counters, voices, the last
GameState the worker saw and the badge state; it is mirrored into
`chrome.storage.session` so an MV3 worker restart does not lose the record.
`__humanplayTtsTest.invokeToggle/speak/stop` is the documented callable test
seam (real key presses cannot be dispatched through CDP). The panel view is
`__humanplayAnalysis.tts` (last decision + decision history).

## Side panel

- **Assistant toggle** — persisted in `chrome.storage.local` under `settings`;
  gates the automatic analysis.
- **Maia suggestion card** — status chip (idle / analyzing… / suggestion ready /
  waiting / game over / server offline / invalid input / engine unavailable),
  top-3 rows (rank, SAN, UCI, probability bar, 1-decimal %, top-1 highlighted),
  WDL chips + perspective label + tooltip, mismatch/warning line, meta line
  (`model … · engine … ms · round-trip … ms · 14 moves · replayed · ui … ms`,
  plus `cached` when the result came from the position cache),
  **Analyze now**, and the two overlay checkboxes (M5): **Show arrows on board**
  (default on) / **Show alternatives** (default off).
- **Elo card** — `elo_self` / `elo_oppo` number inputs + "reset to 2400".
- **Voice (TTS) card (M6)** — **Speak suggestion** (default off, persisted),
  **rate** (0.8/1.0/1.2), **Speak test** ("Knight to f3"), the voices
  availability line + actionable note, and a hint with the Ctrl+Shift+Y hotkey
  and the badge. Speech runs in the service worker (survives closing the panel).
- **chess.com game state card (M3)** — listening chip, board id, exact FEN,
  move count + history status, side to move, your color (+how it was detected),
  mismatch warning, warnings line, source/strategy line. **Refresh state** asks
  the active tab's content script. **fallback color** (`auto`/`white`/`black`)
  is the manual override when detection breaks on a page variant. **Record
  chess.com snapshot** (sanitized JSON corpus).
- **Debug tools (M2)** — **Capture now** (one frame through the locked
  capture-source abstraction) and **Record fixture (PNG)** (downloads the last
  frame via `chrome.downloads`). Screenshot data URLs are never written to
  storage; the last frame lives in memory only.
- **Server chip** — `GET http://127.0.0.1:8765/health` (2.5 s timeout).

## Permissions (important)

- `content_scripts` / `web_accessible_resources`: only
  `https://www.chess.com/*` and `https://chess.com/*`. **No `<all_urls>`** in
  the shipped manifest.
- `host_permissions`: only `http://127.0.0.1:8765/*` (`/health`, `/analyze`,
  snapshot upload).
- `tts` (M6): speak through `chrome.tts` **from the service worker** (verified
  available there on Chrome 155 — no offscreen document, so no `offscreen`
  permission). No additional permissions were added for M6.
- `commands.toggle-tts` (Ctrl+Shift+Y): toggles TTS from the worker; the
  toolbar badge shows "TTS" while on. No permission required.
- Tab capture (debug tool) uses `activeTab`: Chromium requires **activeTab or
  `<all_urls>`** for `chrome.tabs.captureVisibleTab`
  (`permissions_data.cc`, `CanCaptureVisiblePage`, `kActiveTabOrAllUrls`); a
  narrow host permission is not enough. Clicking the toolbar icon on the tab is
  what grants it — which is also how the side panel opens.

browser runs use Chrome for Testing:

```bash
npx --yes @puppeteer/browsers install chrome@stable --path "$HOME/.cache/humanplay-chrome"
# binary: $HOME/.cache/humanplay-chrome/chrome/linux-155.0.8059.84/chrome-linux64/chrome
```

## Boundaries

No Maia-3 code here, ever — the extension is a clean-room HTTP client for the
separate local server (`../docs/PROJECT.md`). The only vendored runtime file is
`vendor/chess.js` (BSD-2-Clause, pinned). No anti-detection features, no
Stockfish, no telemetry. The adapter only reads; the **only** thing the extension
adds to a chess.com page is the single click-transparent overlay canvas. TTS is
`chrome.tts` from the service worker (no offscreen document, no new host
permissions).
